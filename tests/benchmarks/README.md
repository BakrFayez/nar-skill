# Benchmarks and independent-oracle harnesses

This directory holds two kinds of material:

- **Timing baselines** — `baseline-*.json`, produced by
  `run_benchmarks.py` and gated by `check_regression.py`.
  These compare NAR now against NAR before (wall-clock and
  memory). They are drift alarms, not correctness evidence:
  a wrong-but-stable result passes them.
- **Independent-oracle differentials** — `oracle_dexdump.py`
  and `oracle_inventory.py`, added in the field-fix round
  for Area 7 (findings F-25 / F-26). These compare NAR's
  output against expectations computed by something that is
  not NAR, on small committed synthetic fixtures, so the
  comparison re-runs in CI-sized time on every change. They
  are the committed successor of the strong certification
  campaigns (Phase 2 / Phase 5), which live out-of-repo and
  therefore never re-run.

## What is measured, and by which oracle

### DEX / disassembly — `oracle_dexdump.py`

- **Measured:** per DEX file — header table sizes (string /
  type / proto / field / method ids, class defs); class
  count and descriptor set; per-class defined method and
  field counts; per-method `insns` size (16-bit code units)
  and real instruction count, keyed by class descriptor +
  method name + full prototype signature, plus totals and a
  per-method multiset digest.
- **Oracle:** the Android SDK `dexdump` binary (its `-f`
  header dump and `-d` disassembly). The expected side is
  parsed from dexdump's output only; NAR
  (`scripts/narlib/dex.py` for structure,
  `scripts/narlib/dexdis.py` for instruction counts)
  supplies only the actual side. This re-runs, on synthetic
  fixtures, the method behind the preserved Phase 2-era
  record of dexdump agreement (40,837 methods / 773,166
  instructions, in `docs/NAR_TEST_MATRIX.md`) whose harness
  was never committed.
- **dexdump location:** `$NAR_DEXDUMP`, then the newest
  `build-tools` directory under `$ANDROID_HOME` /
  `$ANDROID_SDK_ROOT`, then `PATH`, then the conventional
  SDK locations the repo's own registry searches. When no
  dexdump is found the harness reports *unavailable* (CLI
  exit 2) and the unit tests skip — it never substitutes a
  NAR-derived expectation.
- **Run it:**
  `python3 tests/benchmarks/oracle_dexdump.py <file.dex|file.apk> [--json]`
  (an APK's `classes*.dex` members are extracted and each
  is measured). Exit 0 = agreement, 1 = mismatch with a
  readable diff summary, 2 = unavailable / unreadable.

### Native inventory + JNI census — `oracle_inventory.py`

- **Measured:** on the fixture APK — the library inventory
  (which `lib/**/*.so` members exist); per-library
  `DT_NEEDED` list and JNI export census, compared against
  `nar-native`'s JSON (`libraries`, `needed`, `jni_exports`
  per library); and the engine JNI scan, compared against
  `nar-engines`' JSON (`jni_scan.libraries_scanned`, and
  per-engine `jni_symbols` match counts and library lists
  for the families the fixture exercises).
- **Oracle:** Python `zipfile`'s member list for the
  inventory, and a minimal independent ELF dynamic-symbol
  reader written inside the harness itself
  (struct-based; it does not import `narlib` — an oracle
  that shares the parser under test cannot catch that
  parser's misreading). When `readelf` is present, its
  `-d -s -W` output cross-checks the in-harness reader, and
  a disagreement between the two oracles is reported as an
  oracle self-check diff. One bounded exception: which JNI
  prefixes belong to which engine family is declared data
  (`scripts/formats.json`); the harness reads that data
  file — never `narlib` code — and applies the prefixes to
  its own census, so the engine block checks nar-engines'
  counting and attribution given the declared markers,
  while the ELF fact layer is fully independent.
- **Run it:**
  `python3 tests/benchmarks/oracle_inventory.py <file.apk> [--json]`
  Exit 0 = agreement, 1 = mismatch, 2 = tooling error.

Both harnesses are wired as tests in
`tests/unit/test_oracle_harness.py`, including
planted-discrepancy tests: a mutated fixture copy and
deliberately offset fact sets must produce mismatches. A
harness that cannot fail is not an oracle.

## Fixture provenance (SYNTHETIC)

The fixtures under `fixtures/` are generated by the
committed builder script `build_oracle_fixtures.py`
(regenerate with
`python3 tests/benchmarks/build_oracle_fixtures.py`):

- `oracle_basic.dex`, `oracle_branches.dex`,
  `oracle_multi.dex` — tiny DEX files built with the repo's
  own synthetic DEX builder (the `DexBuilder` in
  `tests/unit/test_dexdis.py`), covering simple methods,
  branches with all three payload pseudo-instructions,
  multiple classes, and a method with no code item.
- `oracle_inventory.apk` — one `classes.dex`, two
  `lib/**/*.so` members built with the minimal ELF builder
  in the same script (one exporting `Java_*` JNI symbols
  with `DT_NEEDED` entries, one plain), and one non-native
  member.

All class, method, library and symbol names in the
fixtures are invented for them; no real target data is
read or embedded, and each fixture is under 16 KB.
**Inputs may be builder-made; expectations never are.**
No expected value is stored anywhere: every expectation is
computed live by the oracle at run time, never recorded
from NAR output. The inventory results carry the label
**SYNTHETIC** in text and JSON output: these fixtures prove
the differential mechanism and the ELF/DEX fact layer on
known inputs — they are not real-target accuracy evidence.

## What remains UNMEASURED

These harnesses close the *re-runnability* gap for two fact
layers (DEX/disassembly, native inventory/JNI census). The
following remain without independent-oracle measurement,
and this README states that rather than implying coverage:

- **Security-finding accuracy is NONE.** This is by the
  anti-circularity refusal already encoded in
  `tests/accuracy/run_accuracy.py`: there is no labeled
  security-findings corpus, findings are deterministic rule
  outputs, and inventing ground-truth labels from the rules
  themselves would be circular. It is stated here, not
  fixed here — closing it needs confirmed *and* refuted
  findings per target, labeled by a reviewer who is not the
  rule author.
- **Atlas** — no oracle scoring anywhere; synthetic
  plist/atlas fixtures only.
- **Fingerprint / strings / report quality** — schema and
  rendering tests only; no external truth source.
- **Decompile-rung output quality** — fallback-chain tests
  pin behaviour under absence/failure with fake tools, and
  the field round confirmed the fidelity *records* are
  honest; the correctness of what a real rung (e.g. a
  decompiler) returns is not oracle-scored.
- **Per-family engine rates** — the corpus-level engine
  measurement exists (out-of-repo Phase 2), but every
  family has too few positives for a per-family rate;
  NOT MEASURED everywhere.
- **The long tail of engine deep-dives** — most of the 26
  family deep-dive tools rest on synthetic fixtures only;
  the strong pockets (some container formats verified
  byte-for-byte against independent parses) are individual,
  not a general gate.
- **Native-library identification** (which library a
  statically linked blob *is*, as opposed to the ELF fact
  layer measured here) — NOT MEASURED; no labeled corpus.
- **Ask / blueprint / compare** beyond the one-off
  out-of-repo Phase 5 campaign, and **endpoint
  classification on real targets** in-repo — see
  `tests/accuracy/` and `docs/NAR_ACCURACY_REPORT.md` for
  the standing per-domain verdicts.
